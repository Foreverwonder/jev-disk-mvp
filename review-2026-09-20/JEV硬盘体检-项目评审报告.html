一句话结论：这不是"一个能用的清理工具"，是一份拿真实磁盘当靶子的 JEV 能力研究报告， 而它把"AI 会承认自己看不懂"这件事做成了可截图的产品。定位站得住、证据链完整、文档量级远超这类个人项目的常态。 真正拖后腿的不是设计，是收尾一致性——同一套修复只做了一半，以及几处"自称的数字和真实数字对不上"。
41.5/ 50
五个维度里，定位（9.0）和文档（8.5）、交互（8.5）是强项； 可用性（7.5）因为三个实测出来的健壮性缺口被压分——但注意：这三个缺口都是收尾问题，不是能力问题。

01评分总览

每项 10 分制。评分依据全部来自实测或代码原文，不含印象分。

交互设计

8.5 /10

凭什么给到 8.5

  • 按"动作"分组，不按模型档位分组。理由写得很清楚：用户只有两个动作，删或不删。这是想过的，不是抄的。
  • 把认知边界摊开给用户改。「判断口径」面板能看到喂给模型的全部问题与选项，改完一键重判还有新旧 diff——这一步把黑箱变成了可辩论的对象。
  • 不确定性被做成了视觉语言：概率分布条、摇摆标记、把握度分压、三档筛选。
  • 为"截图发出去"专门设计：三态脱敏（关／遮路径／遮路径+文件名）、文件名命中敏感词弹红色提醒。
  • 状态反馈完整：进度条、四关阶段文案、中止、错误、空态、结果缓存回放。

扣在哪

  • 键盘与无障碍基本为零。弹窗没有 Esc、行不能方向键选、button 没有 focus 样式、纯 div 表格对读屏器不友好。
  • 长列表全量重绘。每次渲染重建整个 #rows，分组计数里还有一处按组过滤的重复扫描，叠加 700ms 轮询，行数一多就闪。
  • 轮询有竞态。重判或新扫描时旧轮询没被作废，旧任务返回的数据还能追加上去。
  • 阈值有两套。分组用的是可配置的 warn_conf，行颜色和分档 chip 里却写死了 0.4／0.6 —— 改了口径，颜色和分组会对不上。

可用性

7.5 /10

凭什么给到 7.5

  • 双击 start.bat 就跑完。自动找 Python、自动开浏览器、首次粘贴 key 后不再问；零第三方依赖，纯标准库。
  • 没人用 20 分钟自动退出，不留后台残骸；关窗口就等于停服务。
  • 能中止（遍历／归纳／签名三处都有检查点）、文件数超限会明说"结果不完整"。
  • 每次扫描都落缓存，可"载入上次结果"回放——录屏时不用重跑，这条是为演示专门加的。
  • 性能实测可信：我独立复核 D 盘 121 万文件遍历 8.2 秒（≈14.8 万文件/秒），与它声称的 11.5 万文件/秒同量级，没有吹。

扣在哪（三条是我实测出来的）

  • 一批请求失败，整个任务就废，已判结果全丢。实测注入"一半批次失败"→ 异常直接冒到任务层，已经成功判完的那些批一个字都没留下。这是录屏现场最大的风险。
  • 模型少回一个 confidence 字段就崩。实测 → TypeError，同样是全任务作废。
  • "点开看里面"和主扫描口径不一致。同一台机器、D 盘 7,745 个 junction，主扫描跳它、"看里面"却钻进去——实测同一个目录 0 个文件 vs 20,000 个文件。
  • key 明文落在 key.txt（虽已进 .gitignore）。

项目文档完整性

8.5 /10

凭什么给到 8.5

  • 17 份文档、约 138 KB，设计史从 v2 一路留到 v8，能看出思路怎么被推翻的。
  • HANDOFF.md 是我见过的个人项目里质量前列的交接文档：一句话定位、"代码 vs 模型谁在干活"的分工表、7 条关键决策、13 条踩坑表、文件地图，连"本机 shell 是坏的"都写了。
  • JEV-功劳核查.md 主动把自己写的规则和模型给的判断分开记账——还如实写了"我的规则 8 条全判反了"。愿意给自己记负分，这在个人项目里非常少见。
  • README 有"已知边界"章节，把做不到的事明写出来（看不懂文件内容、不知道你还在不在用）。

扣在哪

  • 一张真截图都没有。只有字符画的界面设计稿，外部读者无从判断成品长什么样。
  • 不是 git 仓库。没有版本历史、没有 LICENSE、没有 CHANGELOG。
  • 没有架构图，数据流只靠文字分工表描述。
  • 测试不是可复跑的文件。四关编排的 20 项断言写在审查报告里，没有落地成测试脚本——下次改代码，这 20 项无法自动重跑。
  • 数字会腐烂。文档里留了两处互相打架的旧值（star 数 342 vs 697）、文件数 208,250 vs 208,283，还残留着"os.walk 扫的"这种代码里早已不用的表述。
  • 有一句准备拿去传播的结论，被自己更晚的证据推翻了（详见下面第 5 条缺口）。这不是造假的错，是"从一批样本上得出的规律被当成了通用规律"——但它出现在最显眼的位置，发出去之前必须改口。
  • 同类信息散在三处：README 面向用户、HANDOFF 面向接手者、docs 面向自己。没有一份"给外部读者看"的入口文档——真有人点开你的分享，他该先看哪份？

项目意图与定位

9.0 /10

凭什么给到 9.0 —— 这是全项目最强的一环

  • 定位选了反面：反 360。"别的清理工具替你下判断，这个工具告诉你它有多不确定。"在同质化的 AI 晒图里，这是稀缺角度。
  • 对自己的定位没有装。计划书第一行就写"目标是做一点能吹牛、能截图、能录屏的东西，不是真清理工具"——把野心和边界一起说清楚。
  • 意图与实现高度一致。全程只读、界面里清清楚楚没有任何删除入口。更关键的是：发现之前多份文档里写着"删除按钮是演示态"，而代码里根本没有这个按钮，于是公开改口并留下记录。为了不吹牛，宁可承认自己之前写的是空头承诺。
  • 审查报告 L5 自己写了最有力的推翻角度，然后承认"这次演示数据太干净，是边界"。

扣在哪

  • 定位里有没解开的张力：一个"只负责看"的工具，最后一步必须用户自己去资源管理器动手；它自己也承认"不是清理建议的权威"。这决定了它的传播价值大于使用价值——倒也不影响它原本的目标。
  • 5 GB 安全闸是个后加的补丁，不是体系。它来自一次真实危险（差点误删正在用的模型），补得很及时，但"模型判错时靠什么兜底"没有被系统化成一条通用规则——本次实测里就有一条 2.895 GB 的条目从 5 GB 的缝里穿了过去。

第一性原理执行落地

8.0 /10

凭什么给到 8.0

  • 第一性原理真的落到了代码里，不是写在 PPT 上：删错代价远大于少删 → 置信度做折扣不做加分；mtime 只加不减（否则误伤活跃缓存）；类别给可删性设上限（模型确实把"程序本体"判成过可删）；结论词语义锚定而非数值切档（按数值切会让顶档永远空）。每一条都能指到具体代码。
  • 性能是真做了根因分析：发现 os.stat 每文件都要 CreateFile 会被杀软逐个拦，改用 scandir 复用 DirEntry 缓存（8 倍）；发现 islink() 对 junction 返回 False、必须查重解析位（重入 pnpm 联接网）；发现归纳是 O(候选目录 × 文件数)，重写成两趟 O(目录)。
  • 编排不是花架子，省钱有数：我端到端实跑 E:\whisper_models——158 文件／8 条压成 6 类／4 次请求／6,806 input token／$0.000286／3.0 秒。
  • 成果可独立验证：它 3 秒内指出的唯一一条"可以删"，正是 whisper-large-v3-openvino\encoder（2.895 GB）——我打开这个目录核实过，里面干干净净只有一个 model_cache，是真正可再生的那 2.9 GB。人工核查了半天的结论，工具自己指到了同一个地方。

扣在哪

  • 同一套第一性原理只传导了一半。主扫描路径改掉了 junction 和 os.stat，"点开看里面"那条路径一行没改——正好是同一个坑。这说明修复是按"哪里疼修哪里"做的，没有回头扫同类。
  • 打分模型的参数只有 30 条小样校准（置信折扣下限 0.6、陈旧加成 0.25、满额 365 天、各类别封顶）。样本太小，换目录要重新看——文档自己也承认了。
  • 技术债作者自己记了：定档逻辑散在两处（第 2 关直判 + 第 3 关 verdict_of），将来改档位要两处一起改。
  • 全项目没有一个自动化测试文件。

04五个值得先修的缺口

严重度按"会不会在录屏现场翻车"和"会不会让懂行的人一眼看穿"来排。前四条是代码，第五条是说法。

1 · 一批请求失败 → 整个扫描作废 最高优

server.py · judge_pipeline 的 round_run（约 L761-762）＋ run_job 的异常分支（L969-972）

并发器是 list(ex.map(work, batches))，任何一批抛异常都会在迭代时冒出去，一路穿到 run_job；而 run_job 的 except 只写 job["error"] 和 job["trace"]，从不写 job["items"]。

后果很具体：你扫 2,000 条、跑到第 30 批的时候网络抖一下，前面 29 批白跑了，屏幕上只剩一行报错。录屏演示时这等于把之前所有镜头废掉。

改法很小：在 round_run 里把 work 包一层 try/except，失败的批记进 job["batch_errors"] 并保持该类的字段为 None；汇总时跳过未判的并提示"本次有 N 批未判"。已判的部分照常出结果。

2 · 模型少给一个字段就崩 同一处改动可一并解决

server.py · score_entry L626 · verdict_of 调用处 L882 · row_conf 计算 L882

score_entry 里 min(1.0, conf) 和 row_conf = min([x for x in (dc, kc) if x is not None] or [dc]) 都没有兜住 None。实测把答案里的 confidence 拿掉，直接 TypeError。

这不是假想场景：noul 类型的返回本来就没有 confidence（笔记里写明了），不同原语字段不一样，靠"默认一定有"是赌运气。

改法：取置信度时统一走一个小函数 _conf(x, default=0.0)，缺字段就当 0 处理（缺字段本来就等于"它没表态"，压向别删是正确方向）。

3 · junction 只修了主扫描，没修"点开看里面" 我自己挖出来的

server.py · expand_dir L69-81（仍在用 os.walk + os.path.islink + os.stat 全路径）

主扫描里那三个坑写得明明白白（os.walk 会走进 junction、islink 拦不住、os.stat 慢 8 倍），expand_dir 却三个坑一个不落全踩了。同一份代码、同一个 bug、修了一半。

实测对照：D:\dshbuild\clean-home2\profiles\node_modules（510 个 junction 子目录）——主扫描返回 0 个文件，expand_dir 返回 20,000 个文件（撞上限）并用掉 1.71 秒。

用户看到的是：点开某一行"看里面"，里面的体积比这一行本身显示的还大。一个把"我承认我不确定"当卖点的工具，自己内部两组数字打架，这是最伤信任的失分点。

改法：expand_dir 直接改成复用 collect_files（它已经处理好了重解析位和 DirEntry 缓存），或至少把判断条件抄过来。大约 30 行。

4 · 界面自称的调用次数和真实调用次数不一致 我自己挖出来的

server.py · L965-966

"完成 · %d 条归并成 %d 类，只判了 %d 次" % (entries, classes, classes) —— 第三个占位符填的是类数，不是请求次数。实测这次屏幕上会写"只判了 6 次"，而同一个屏右下角的用量脚注写着 requests: 4。

为什么这条值得单独拎出来：这个项目的审查报告里，抓得最狠的就是"文档写了代码里没有的东西"。这条属于同一个病，在四个版本、多轮对抗性审查之后活了下来。改一行的事——把第三个参数换成 job["usage"]["requests"]。

5 · 最漂亮的那句结论，被项目自己更晚的证据推翻了 口径问题，传播前必须改口

docs/JEV演示工具-计划书.md 附录（2026-09-20 凌晨） vs docs/JEV-功劳核查.md 第三节（同日 12:41）

计划书末尾留了一句准备拿去传播的结论："错判全部落在它自己说'我没把握'的那一堆里。"这句话在它当时那批 30 个样本上站得住——6 个错判（.git 哈希名文件）的自报把握度是 0.00~0.17。

但同一天更晚、样本更认真的那份《功劳核查》里，E 盘 48 条只错了 1 条，而那一条恰好是最重要的那个：37GB 的 whisper_models 被它判成"可再生缓存"，把握度 0.62——不难看，也不算低。真正拦住它的是那道 5GB 的硬闸门，不是把握度。

所以那句营销话如果原样发出去，懂行的人只要问一句"那 0.62 那次怎么算"就破了。而真实情况反而更有说服力：小错它自己知道在猜（把握度 0.0~0.17），最危险的错它是真信了（0.62）。"看错"和"想歪"是两回事——前者靠把握度就能筛掉，后者必须靠不看模型脸色的硬闸门兜底。

建议：把结论升级成两层版本，并在 README 里把这条口径记下来。传播包里我已经按这个版本重写了，直接用那一版。

05后续计划：六个候选（按性价比排序）

方向都朝着同一个目标：把"AI 会承认没把握"这个稀缺点，变成能反复出内容的内容源。

A · JEV vs 大模型 同题对照跑

★★★★★

同一个目录，JEV 判一遍、某个通用大模型判一遍，把耗时／成本／一致性三列并排。

这是全篇含金量最高的内容：硬数字、可复现、天生适合当封面图。厂商宣称 193.6x 更快、444.6x 更便宜——你现场跑出你自己的数字，比转述厂商有说服力得多。

工作量 小适合 公众号＋朋友圈风险 低

B · 「它认怂指数」单页报告

★★★★★

扫完直接出一张图，头条不是"能省多少 GB"，而是"这次扫的 N 条里，它敢拍胸脯的只有 X%"，下面按把握度分三堆。

别人晒 AI 都在晒"它多准"，你晒"它知道自己不准"——这就是计划书里那句"最有品味"的展示，而它现在还没被做成成品。

工作量 小适合 小红书＋朋友圈风险 低

C · 误判博物馆（持续累积）

★★★★☆

专门收集"判错 + 它自己把握也低"的案例，一条条存档，做成一个越攒越厚的展馆。

最有力的一句已经在你手上："错判全部落在它自己说'我没把握'的那一堆里。"这句有真实数据支撑，而且能长期更新——每换一台机器、每扫一个新目录都能加一条。

工作量 极小适合 系列内容风险 低

D · 人机对赌：你先判，它再揭晓

★★★★☆

你先给每条写"删／留"，然后揭晓模型的答案，统计"人机分歧率"和"谁更保守"。

互动性最强的一种：能做成公众号的投票、朋友圈的"你觉得这条能不能删"。副产品是一份真实的人机对齐数据，比单纯展示工具更有研究味。

工作量 中适合 互动内容风险 中（要避开隐私文件）

E · "删除代价秤"可视化

★★★☆☆

把 JEV 返回的四档损失分布做成一台天平：候选放左盘，四档权重块按概率大小落到右盘。

纯视觉记忆点，一眼就懂"它在权衡"。适合做录屏里的高光镜头，也适合当封面。但它依赖前端动画工作量，属于锦上添花。

06下一步可落地的优化方案

P0 三条建议在录屏之前改完，全是小改动、低风险，直接决定镜头能不能一次过。

P0
让单批失败不拖垮整个任务
在 round_run 的 work 外层加 try/except，失败批记进 job["batch_errors"]；汇总循环里遇到未判的类跳过并在界面提示"本次 N 批未判"。这是录屏现场唯一的保单。
server.py · judge_pipeline / round_run · run_job
P0
置信度缺字段一律兜成 0，不抛异常
统一用一个取值函数：拿不到 confidence 就当 0（缺字段＝它没表态，压向"别删"是对的方向）。顺手把 score_entry、row_conf 两处都套上。
server.py · score_entry L626 / L882
P0
修掉"点开看里面"和主扫描的口径差
让 expand_dir 复用 collect_files（重解析位 + DirEntry 缓存都是现成的），顺手把 total_size 在截断时改为如实标注"至少 N GB"。改完两组数字就不会再互相打脸。
server.py · expand_dir L64-94
P0
把"只判了 N 次"改成真实请求数
第三个占位符换成 job["usage"]["requests"]。一行改动，让同一屏上的两个数字对上。
server.py · L965-966
P1
口径单点化：干掉写死的 0.4 / 0.6
行颜色、分档 chip、四档筛选全部改读 UI.warn_conf 与 rules.low_conf_threshold，让"改口径"真的能全局生效——不然那个很漂亮的"一键重判"会给出前后矛盾的界面。

P1

每次 startScan／重判时递增一个 token，回调里比对不上就丢弃。顺手把 visibilitychange 与定时器的叠加收掉，避免切标签页繁殖出多个监视循环。
index.html · poll() / watchJobs()
P1
行渲染改增量，去掉 O(n²) 分组计数
每组的计数算一次缓存起来，只在数据真变化时更新受影响的行——现在是每次轮询全量重建整个表格，几百行就会肉眼可见地闪。

07一句话定位（可以直接用）

「我给 AI 装了个刹车，然后让它自己承认踩不住。」

别的清理工具是黑箱裁判，一口咬定"可以删"。这个不。它每给一条建议，都得附上自己的把握度； 连"这是什么东西"都没把握的，直接标"看不懂"，不许进建议删的那一档。 它的价值不在替你多做决定，而在让自己少做错的决定。

评审方式：文档全量阅读 + 代码逐行审查（server.py 1,366 行 / index.html 1,109 行）＋ 端到端实跑（真实 API）＋ 三项故障注入 ＋ 独立复核。 所有"实测"字样均为本机真实执行结果；所有"声称"字样均引自项目自带的 docs/，并已标注是否复核。 评审未改动项目任何代码或配置；唯一的落盘副作用是实跑一次扫描时工具自己写的 cache/20260920-151102.json（已在 .gitignore 里，可随时删）。
