## 一、现场

扫 C:\ 读到 **1,122,878 个文件**、跳过 3,044 个 junction，卡在「正在归纳条目…」，然后：

```
OSError: [Errno 22] Invalid argument
  server.py line 1071  run_job        → build_entries(root, files, ...)
  server.py line  536  build_entries  → entries.append(entry_dir(d, total, cnt))
  server.py line  475  entry_dir      → time.strftime("%Y-%m-%d", time.localtime(oldest))
                                          ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ ^^^^^^^
```

112 万文件读了 16 秒，到这一步全白跑。

## 二、根因：NTFS 上真的有 1601 年

### 2.1 平台行为（实测，不是查文档猜的）

| 输入 | `time.localtime()` |
|---|---|
| `0` / `1` | OK |
| **`-1`** | ❌ `OSError: [Errno 22] Invalid argument` |
| `-86400` / `-2208988800` / `-11644473600` | ❌ 同上 |
| `253402300799`（9999 年）/ `1e12` | ❌ 同上 |
| `nan` | ❌ `ValueError` |
| `inf` / `-inf` | ❌ `OverflowError` |
| `32536799999`（3001 年） | OK（**所以上限是"我们的策略"，不是平台边界**）|

**Windows 的 CRT 不接受负时间戳**，`gmtime` 同样。

### 2.2 元凶：5 个文件

全盘扫了 **135.8 万个文件**，负时间戳的只有 5 个 —— 而且全在一个地方：

```
C:\Users\<user>\AppData\LocalLow\Tencent\WeType\Dict\bwcjp\1169\bwcjpmac_jianpin.bin
C:\Users\<user>\AppData\LocalLow\Tencent\WeType\Dict\bwcn\1346\bwcnmac.bin
C:\Users\<user>\AppData\LocalLow\Tencent\WeType\Dict\bwcnmacv8\39\bwcnmacv8.bin
C:\Users\<user>\AppData\LocalLow\Tencent\WeType\Dict\ckvd\456\ckvdmac.bin
C:\Users\<user>\AppData\LocalLow\Tencent\WeType\Dict\slwd\1306\slwd_pc_second_level.bin

mtime = -11644318675.68624   ≈ 公元 1601 年
```

微信输入法的词典文件。**资源管理器自己也显示 `01/03/1601 03:02:04`** ——
不是 Python 的视角问题，是 NTFS 上真这么存着。

> 5 个文件 → 112 万文件的扫描全废。这就是"一个坏数据点能带走整批"的样子。

### 2.3 比"会崩"更麻烦的：污染聚合

就算把 `strftime` 包一层 `try` 让它不崩，**结论还是错的**：

```python
# build_entries 的 Pass A
if n["lo"] is None or m < n["lo"]:
    n["lo"] = m          # lo = 该目录下所有文件 mtime 的最小值
```

混进一个 `-11644318675`，整个目录的「最老内容」就变成 1601 年 →
**年代视图会把微信输入法目录归进 1969 年前**，而这个目录其实是今年还在动的。

⇒ **过滤必须放在聚合之前，不能只包住格式化。**

## 三、改了六处

| # | 改什么 | 为什么 |
|---|---|---|
| 1 | 新增 `safe_epoch(ts)` / `fmt_date(ts)` | 坏的收敛成 `None` / `"未知"`，**绝不抛** |
| 2 | **`lo` / `hi` 聚合前先过滤** | 治的是污染的源头，不是症状 |
| 3 | `idle_days()` 坏值返回 `None` | 老实现算出 **155488 天**（15.5 万年） |
| 4 | **下游两处跟着接受 `None`** | `score_entry` 的浮点除法、汇总的 `round(None)` —— 不改就是 `TypeError` |
| 5 | 新增 `degraded_entry()` | 单条构造失败就**降级保留体积和文件数**，不再让一个条目掀掉整场 |
| 6 | 前端年代视图 | 非 4 位年份显示「时间未知」，不再是「未知 年」 |

**第 4 条值得单说**：它是**这次修复自己带出来的**回归风险。
把 `idle_days()` 的返回值语义从"永远 float"改成"可能 None"，如果只改定义处、不 grep 调用点，
就会在打分和汇总两处 `TypeError`。**改函数返回值语义前，先 grep 出全部调用点。**

第 5 条的取舍：**丢条目等于凭空少一块体积**，用户会以为自己盘里就这些。
降级保留（时间标未知、体积照留）比丢掉诚实。

## 五、这次留下的两条通用教训

1. **"坏数据"有两个层次：让格式化崩，和让聚合错。** 只堵前者，后者会静默地把结论带歪 ——
   而静默的错误比崩溃危险（崩溃至少你会知道）。
2. **改函数返回值语义 = 改契约。** 定义处改完必须 grep 全部调用点，
   否则"修 A 带出 B"。这次靠 `grep -n "idle_days" server.py` 找出 4 处才没漏。
