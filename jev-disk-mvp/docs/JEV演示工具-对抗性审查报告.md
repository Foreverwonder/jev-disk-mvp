## L1 事实层

| 判定 | 内容 |
|---|---|
| ❌ **硬错** | **"界面上的删除按钮是演示态"—— 这句话在代码里根本不存在。** 实测：`index.html` 里没有任何删除入口。而我在**计划书、设计 v3、README、最终回复**里至少说过 4 次。这是"描述了一个不存在的功能"，比算错数字严重 |
| ❌ **硬错** | **"3 道问句"** —— 实现是 **2 道**。而且是**同一份文件自相矛盾**：`界面字符图.md` 的图 1 写"3 道问句"，图 6 却只画了问题①② |
| ❌ **以偏概全** | **"扫描 65ms / 全程 1.7 秒"** —— 那是 `Downloads` 这组最好看的特例。实测 `AppData\Local`（28 万文件）要 **13 秒**。我把特例当一般结论报了 |
| ❌ **漏做** | `truncated`（扫描被截断）后端算了、API 也返回了，但**前端从未展示** —— 用户拿到不完整结果却不知道 |
| ❌ **漏做** | `kind_conf`（类别判断的置信度）后端每条都取了，**前端一列都没显示** |
| ✅ 站得住 | 48 条目 / 3033 文件 / 分档统计 / token 数（29,158）/ 花费换算（$0.042 per Mtok → $0.001225）—— 全部可复现 |
| ✅ 站得住 | 判定规则 `verdict_of` 与设计 v5 的规则表逐条对得上 |

## L2 口径层

| 判定 | 内容 |
|---|---|
| ❌ **口径不一致** | **「可回收」把"可以考虑"一起算进去了**，而「建议删除」这一档**本次是 0 项**。顶上写着「可回收 959 MB」，读者会理解成"这些可以放心删"——实际是"这些或许可以删"。更糟的是「建议清理 32 项」和「建议删除 0 项」两个标签撞车，读者分不清 |
| ❌ **口径缺失** | **「把握」背后有两个置信度，界面只显示了其中一个。** 实测 `project_20260513_124739.tar.gz`：损失判断把握 **0.65**、类别判断把握 **0.39** → 界面显示 0.65，看着挺确定，可它连"这是什么"都只有 0.39 |
| ❌ **口径错** | **折叠目录的"最后改动时间"用错了量。** 用的是目录自身的 mtime —— 可它会被程序不断改写。实测 `~/.workbuddy/logs`：**目录 mtime = 今天，内部最老内容 = 2026-05-16，差 127 天。** 「年代」视图因此把一个 2026-05 就开始攒的目录算进"今年" |
| ✅ 站得住 | 「可删性」方向统一（越大越该删），上一轮修完后本轮无回退 |

## L3 解读层

| 判定 | 内容 |
|---|---|
| ⚠️ **风险** | **「慎重」这一档的风险跨度极大。** 实测它同时装着：私人聊天记录（`私聊_晨曦✨.json`、`群聊_哲哲污大师班.jsonl`）、QQ 导出的 mp4、以及（另一批数据里）**6 个 `.git` 对象**和**4 个正在用的代理程序**。档位名会诱导"按档处理"，而档内既有"无所谓"也有"删了出事" |

| ✅ 站得住 | 每行的「依据（本地规则）」与 JEV 的判断**分层标注**，没有混为一谈 |

## L4 方法层

| 判定 | 内容 |
|---|---|
| ⚠️ **必须标注是我发明的** | `可删性 = 原始分 × 置信折扣 × 陈旧加成`、四档结论词、`min(两类把握)` 取法、类别封顶表 —— **全部是我发明的，没有任何外部依据**。JEV 本身是厂商的，但**打分公式不是**。上一版文档里我说过"从第一性原理推出"，那是"我自己推的"，不是"有依据的" |
| ⚠️ **一条规则其实常常失效** | **陈旧加成对折叠目录基本不起作用**：目录 mtime 总被刷新 → `age_boost ≈ 1.0`。也就是说"越久没动越想删"这条规则，**对体积最大的那些对象恰恰不生效**。这是"mtime 只加不减"公理的必然结果，方向安全，但要写清楚，别当成卖点 |
| ⚠️ **边界不连续** | `round()` 是银行家舍入：`d_raw = 2.5` → 落到「可以考虑」，`2.51` → 跳到「建议删除」。阈值不透明 |
| ✅ 站得住 | kind 与 deletability 的**一致性守卫**（程序本体 ≤1.0 等）真的拦住了代理程序那批，实测生效 |

## L5 元层

| 判定 | 内容 |
|---|---|
| ⚠️ **虚假精确** | `可删性 2.42/3`、`把握 0.58` —— 两位小数。可证据只有"文件名 + 体积 + 时间"，撑不起这个精度 |
| ⚠️ **目的本身有风险** | 目标是"截图发朋友圈/小红书"。实测扫 `Downloads` 就命中 **4 个隐私文件名**。原设计只挡路径、不挡文件名 |
| ⚠️ **可复现性** | JEV 非确定性（概率抖 ±0.03）→ 同一目录扫两次，排序可能微变。**录屏两次结果不会完全一致** |
| ⚠️ 结论定位 | 应表述为「**体检报告的初筛**」，不是「清理建议书」。任何"这个可以删"都要回到人 |

### 未修（留给你拍板，4 项）

1. **要不要真的加一个"演示态删除按钮"？** 我倾向**不加**——加了反而误导（一个不能用的删除钮比没有更糟）。但如果你录屏需要那个"爽感"，可以加，并且必须明确标注。
2. **文件夹选择器不显示大小** —— 现在是盲选。要加得给每个子目录做一次浅遍历，弹窗会变慢。
3. **`可删性` 两位小数的虚假精确** —— 改成一档一档的粗颗粒？还是保留？
4. **JOBS 字典和 cache 目录无清理** —— 长时间开着会慢慢吃内存和磁盘。

## 审查意见复核（我验证后**不采纳**的）

- **我原本怀疑"年代视图对文件夹失真"是 `age_boost` 的 bug。复核后不采纳**：age_boost 用目录 mtime 是"只加不减"公理的必然结果，方向安全（不加成 ≠ 误伤）。真正的错在**展示口径**，已改为用 `mtime_oldest` 归年。
- **我原本怀疑 `$Recycle.Bin` 没被过滤 → 复核确认是真 bug**（大小写敏感 + 层级两个原因），已修。
- **我自己写的第一版"中止"修复 → 复查时被自己推翻**，已重写。
