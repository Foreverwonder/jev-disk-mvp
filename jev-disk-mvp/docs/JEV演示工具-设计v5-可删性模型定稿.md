## 0. 先回答：实时扫描，还是提前扫好再喂进去？

**能做到真·实时，而且有实测数据支撑：**

| 环节 | 实测耗时 |
|---|---|
| 扫描 30 个对象（含 2 万个文件的目录遍历） | **1 秒** |

## 1. 我自己审查后改掉的 5 处

| # | 原设计 | 问题 | 改法 |
|---|---|---|---|
| 1 | 3 道问句：类别 / 保留价值 / 删了后悔 | **「保留价值」和「删了后悔」语义重复**（价值低 ≈ 删了不后悔）。问两遍浪费 token，而且两者不一致时用户无所适从 | **砍成 2 道**：类别 + 删除损失 |
| 2 | 置信度只是展示，不进公式 | 一个「置信 0.02 的建议删除」和一个「置信 0.95 的建议删除」排一起 | 置信度做**折扣系数**（0.6 ~ 1.0） |
| 3 | 没用最后改动时间 | 漏掉一个强信号 | 做**只加不减**的陈旧加成 |
| 4 | 体积没进排序 | 2.71 GB 的 logs 排到第 19 名，一个 29 MB 的 apk 排第 1 | 分档后**组内按体积降序** |
| 5 | `kind`（是什么）和 `deletability`（该不该删）互不约束 | **逻辑矛盾**：代理内核 `xray.exe` 被判成「程序本体」却给了 2.18 的删除分 | 加**一致性守卫**：`kind` 同时给数值和结论设上限 |

**第 5 条是最重要的一处。** 它说明：光靠模型自己判不够，必须有一层规则去拦它自相矛盾的地方。

## 2. 可删性的推导（第一性原理）

### 2.1 先问：什么叫「该删」？

不是"这东西有用吗"，而是 **"删了以后，损失大不大"**。这两个问法不一样：

- "有用吗" → 会让所有东西都显得有用（什么都可能哪天用上）
- "删了损失大吗" → 直接对准决策，而且**天然带不对称性**（损失是负向的）

### 2.2 五条公理

| # | 公理 | 推论 |
|---|---|---|
| 1 | **「该不该删」和「删了值不值」是两件正交的事** | 不能乘成一个数——否则你分不清一个高排名是因为"体积大"还是"确实该删"，信息就丢了 |
| 2 | **删错的代价 >> 少删一点的代价** | 不确定的项必须往"别删"方向**保守化** |
| 3 | **置信度是"能不能信"，不是"该不该删"** | 它做**折扣**，不做加项 |
| 4 | **人对体积的感知是对数的** | 1 MB→100 MB 的收益感 >> 1 GB→1.1 GB，所以体积要**对数压缩** |
| 5 | **mtime 只能往上加，不能往下压** | 见下面这条坑 |

**公理 5 是怎么来的（一个差点踩的坑）**：
我本来想加一条"最近 7 天改动过的 → 保护起来"。但**活跃的缓存目录一直在被程序改写，mtime 非常新，可它照样该删**。
比如 `~/.workbuddy/logs` 今天就动过，但它 100% 可以删。
⇒ 如果 mtime 能往下压，会**大面积误伤活跃缓存**。所以定死：**陈旧只能当加分，永不当减分。**

### 2.3 公式

```
可删性数值 = clamp( d_raw × shrink(conf) × age_boost(idle), 0, cap )

  shrink(c)     = 0.6 + 0.4 × c          c=0 → 打四折；c=1 → 不打折
  age_boost(d)  = 1 + 0.25 × min(1, d/365)   闲置越久加得越多，最多 +25%
  cap           = min( cap_by_kind , cap_by_conf )
```

**为什么 shrink 的下限是 0.6 而不是 0**：完全不信就该丢掉这条判断，但那样会浪费信息。打四折是"保留方向、削弱强度"，让它在排序里下沉但不消失。

### 2.4 cap（一致性守卫）

| 条件 | 上限 |
|---|---|
| `kind = 程序本体 / 应用状态` | **1.0**（绝不能进"建议删除"） |
| `kind = 看不懂` | **1.5** |
| `kind = 用户产出` | 2.0 |
| 置信度 < 0.40 | **1.2** |
| 其余 | 3.0 |

## 3. 结论词：不走数值阈值，走"语义锚定 + 规则降级"

**为什么不用数值切档**：如果按 `可删性 ≥ 2.5` 切，那"建议删除"几乎永远不触发（实测数值最大只有 2.44）。

改用**语义锚定**——标签直接来自模型自己选的档位（这个档位是有语义的、可解释的）：

```
基础结论 = 模型档位:  0 → 别碰   1 → 慎重   2 → 可以考虑   3 → 建议删除

降级规则（取更保守的那个）:
  类别 = 程序本体 / 应用状态 / 看不懂   → 上限「慎重」
  置信度 < 0.40                        → 上限「慎重」
  置信度 < 0.50 且 基础 = 建议删除      → 降为「可以考虑」
```

**置信度门槛为什么是 0.50 而不是 0.60**：实测这类任务上 JEV 的置信度中位数约 **0.55**，
用 0.60 会把过半判断挡在最高档外，最高档直接空掉（我第一次就跑出了空档）。
0.50 是"比抛硬币强"的自然分界。**换数据集时这个门槛要重新校准。**

## 4. 排序

```
主排序：先分档（建议删除 → 可以考虑 → 慎重 → 别碰）
        组内按体积降序
```

**这就是你说的第一性原理 + 体积的结合方式**：分档保证"建议删的在前"，组内按体积保证"大件优先"。
两者不打架，而且比乘成一个数更好——**一眼看得出一个条目排前面，是因为"确实该删"还是因为"它很大"。**

另外保留两个可切换视图（供不同叙事）：
- **能腾多少空间**：`可删性数值 × 体积对数分` 降序（跨组）
- **体积**：纯体积降序

## 6. 还没解决的（诚实清单）

1. **「建议删除」档很小（4/30，0.18 GB）**。
   因为 JEV 极少给满分档（实测 `d_raw` 最大只有 2.58，中位 1.94）——这是它"校准过"的正常表现。
   但代价是最高档永远很小。**如果演示需要更"有料"的顶档，可以把门槛再调低一档，我会标注这是人为放宽。**
2. **归档包和它的解压目录，模型看不出关系**。`project_20260514_175130.tar.gz`(161 MB) 和同目录的解压文件夹，
   需要加一条**代码规则**（比对条目数/文件数）才能识别，不能指望模型。
3. **"最近生成的大文件"没有保护机制**。因为公理 5 定死了 mtime 只加不减，所以昨天刚下载的大文件
   不会被主动保护。可接受（下载目录本来就是要清的），但要知道这个取舍。
4. **置信度门槛 0.50 是按本批 30 条的分布校准的**。换目录、换数据量都要重新校准。
