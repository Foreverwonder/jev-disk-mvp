## 三、诚实记账：这 48 条里，两边各打赢了什么

### 纯规则（我原来那套）的表现

```
有明确规则的条目      8 / 48   ← 全是 .exe/.zip 后缀命中的
只能兜底成「按扩展名
  与位置推断」的      40 / 48   ← 等于"我不知道"
```

**更糟的是：这 8 条它全判反了。**

| 文件 | 我的规则说 | JEV 说 |
|---|---|---|
| ZCode.exe | 安装包后缀（暗示可删） | 程序本体 · 把握 1.00 |
| clashmiService.exe | 安装包后缀 | 程序本体 · 把握 0.99 |
| adb.exe / aapt.exe / aapt2.exe | 安装包后缀 | 程序本体 · 把握 0.90 |
| apkeasytool.exe | 安装包后缀 | 程序本体 · 把握 0.90 |
| 进程树管理.exe | 安装包后缀 | 程序本体 · 把握 0.90 |

这些 .exe 其实都躺在工具目录里（是程序本体，删了软件就坏）。**规则只会看后缀，分不出"安装包"和"程序本体"。**

### JEV 的表现

```
给了类别的条目        48 / 48
逐条纠正上面那 8 个   8 / 8   ← 全部推翻了我的规则
判定错的关键条目      1 / 48  ← 而且恰好是最重要的那条
```

**它错的那一条，正是 `whisper_models` 28.80 GB**：它说「可再生缓存 0.67 / 把握 0.62」，而实际那是**你正在用的转写模型**。删了转写工具当场坏。

**是界面那道闸门把它拦下来的**：`体积 ≥ 5GB → 一律不许进「可以删」`。这条不是 JEV 说的，也不是我原来那套规则，是这轮专门为它加的。

### 所以功劳怎么分

**不是"JEV 当主角"或"规则当主角"，是接力，而且各有各的活：**

```
文件系统  →  提供事实（多大、几个文件、多久没动）          纯数据
JEV      →  提供语义（这是什么、删了亏多少、有多确定）      只有它能干
我的规则  →  提供框架（定档、封顶、分组的闸门）              防止 JEV 判错时出事
```

**按字段个数算**，我的规则占得更多（可删性公式、结论文案、三个分组、依据小字）。但**真正决定性的是"类别"那一个字段** —— 因为结论档位、可删性封顶，全部建立在"它认为这是什么"上面。所以：

> **这一版的可删性判断，地基是 JEV 打的；出问题时，兜底是我的规则。**

要说清楚的一点：**上一版那个"纯代码清理工具"的样子，现在只剩"扫描 + 折叠 + 分组"这三件机械活**。剩下的语义判断——48 条全部——都是 JEV 给的。

## 四、为什么清单看着只有几项

两个原因，一个是设计、一个是现实：

1. **「别动」那 42 项原来默认折叠着** —— 所以首屏只看得见 6 行。**已经改成默认展开了**，现在首屏就是全部 48 行。
2. **E 盘本来就只有 48 个 ≥1MB 的大件**（扫描阈值 `min_size_mb = 1`）。

想要更长的清单，两个办法：
- 把阈值降到 `0.2 MB`（改 `config.json` 的 `scan.min_size_mb`，重扫）
- 换更脏的目录：`C:\Users\<user>\AppData\Local` 那下面有 **28 万个文件**

另外：这 48 条是按特征**归并成 24 类**之后判的，所以 JEV 只被调用了 6 次。
