# 扫描性能修复 · 对抗性审查报告

2026-09-20 · 审查对象：本轮「扫描慢」的修复（collect_files 换 scandir / junction 拦截 / 统计两趟化 / 体积优先配额 / 覆盖率显示）

## 问题的真相（先回答用户的三个疑问）

**「这是 JEV 的限制吗？」—— 不是，一点关系都没有。** JEV 只在判断阶段被调用，这轮实测它全程只花 46 次调用、$0.0117。慢的是我扫描代码里的三个缺陷。

**「是系统的限制吗？」—— 不是。** 实测 D 盘（NVMe SSD）枚举速度可达 10 万+ 文件/秒，118 万个文件全盘只要 12 秒。慢全慢在我的代码上。

| 缺陷 | 实测代价 |
|---|---|
| ① `os.stat()` 逐文件调用（被杀软实时防护拦截放大） | D:\dshbuild 上 9,603 文件/秒 → scandir 后 77,206（**8.0x**） |
| ② `os.path.islink()` 拦不住 junction，走进 pnpm 联接网重复遍历 | D:\ 全盘 8,640 → 110,399 文件/秒（**同条件 8.1x**） |
| ③ children 目录树漏掉「自己不含文件的中间层」 | **D:\wechat 58.94 GB + WeGameApps 57.11 GB 整树凭空消失** |
| ④ 条目配额按字母序「先到先得」 | 600 条配额被小目录吃光，最大的目录反而被挤掉 |
| ⑤ 统计是 O(目录数×文件数) | D:\AI_Projects 归纳要 176 秒 → 两趟化后 2.6 秒 |

**修复后端到端（D 盘全盘 1,186,881 文件）：扫描+归纳+JEV 判断共 29 秒，2000 条覆盖 99%。**

### L2 口径层

| 问题 | 结论 |
|---|---|
| 逻辑大小 vs 磁盘占用 | 界面显示的是**逻辑大小**（st_size）。D 盘已用 194.48 GB vs 扫到 189.76 GB，差 4.72 GB = skip 名单目录 + NTFS 簇对齐浪费。已在报告标注，界面不动（行业惯例同 WizTree） |
| 硬链接重复计数（pnpm 在 Windows 用硬链接） | **实测 0 个共享 inode**（.pnpm-store ↔ AI_Projects/dshbuild 各抽 4000 个文件）——这台机器上不存在，体积不虚高 ✓ |
| junction 的目标 | 抽查 12 个全部指向 `D:\AI_Projects\豆包Test\dsh-build\deepseek-harness` 内部——**不拦截的话同一个项目会被扫两遍**，拦截是正确的 ✓ |
| ★ 审查自己的抽取器 | 第一版硬链接检测用 `DirEntry.stat().st_ino`，Windows 上**全是 0**，检测完全失效——换 `os.stat()` 走完整路径才拿到真 inode。审查工具本身也会错 |

### L3 解读层（每条给反面）

| 结论 | 对面最有力的反驳 | 回应 |
|---|---|---|
| 「快了 8.1 倍」 | 不是机器变快，是原来慢得离谱 | 接受。表述改为「修掉两个具体缺陷后的正常速度」 |
| 「覆盖率 99%」 | 反过来读：之前 84% 意味着**漏看了 30 GB**，用户会以为盘上只有那些 | 接受。所以加了覆盖率显示 + 把 max_items 从 600 提到 2000 |
| 「跳过 7,745 个链接」 | 跳过的内容不计体积，某些目录会被低估 | 抽查证明目标全在扫描范围内，真实位置会被统计到，**不丢数据** ✓ |
| 「JEV 只要一分钱」 | 600→2000 条后成本从 $0.005 涨到 $0.012 | 已如实报 $0.0117，仍可忽略 |

### L4 方法层

- **两趟统计**（先算直接文件、再自底向上合并）：与旧算法的等价性有理论论证（加法可交换、top-8 合并单调、min/max 可结合）+ 38 目录抽查全一致。**抽查不是证明**，已如实标注。
- **体积优先最大堆**：这是我发明的遍历策略，无外部依据——但对照证据明确：字母序先到先得时 wechat（58.94 GB，全场最大）丢失，堆序下恢复且配额花在最大对象上。
- **junction 不跟随**：是决策不是纯技术。理由：① 防重复计数（junction 指向范围内的真实数据）② 防链接环路。代价：如果 junction 指向**扫描范围外**，那部分体积不显示——本机抽查未发现这种情况。

### L5 元层

- 所有速度数字是**本机缓存热状态的一次实测**，换机器/开杀软实时防护会变。相对提升（8x）比绝对值（10 万/秒）更可信。
- 最有力的自我推翻角度：「也许慢根本不是这些缺陷，而是当时有别的东西在占 IO」——反证：同机同时段，同样的目录，只换实现速度差 8.1 倍，变量被隔离 ✓
- 结论定位：**「慢」已定性为代码缺陷并修复，有同条件对照数据；「快多少」给区间（8~10x）不给单点。**
